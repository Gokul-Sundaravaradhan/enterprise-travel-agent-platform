## Goal

Replace the hand-written planner loop with a durable, typed, multi-agent graph that can pause for human approval, and that stays safe when its model is fooled.

## Tool-Call Reliability Design

**Premise.** The model's output is probabilistic text. A system prompt asking for "valid JSON" improves the odds but is not a control, so no tool call may depend on the model being well-formed. Today the agent asks for a JSON plan in free text, extracts it by finding the first and last brace, indexes fields directly (a missing field is a `KeyError`), has no repair or retry, never validates arguments against the tool's schema (which it fetches and only shows to the model), and ignores MCP error results. All of that is replaced here.

| Layer  | Control                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L0** | **Constrain generation.** Use the provider's native structured output where it exists (a JSON schema with Ollama, structured outputs with OpenAI); the mock provider emits schema-valid or deliberately invalid fixtures. This lowers the failure rate and never eliminates it                                                                                                                                        |
| **L1** | **Parse and validate the plan** with Pydantic models: unique step IDs, every dependency exists, no cycles, a step cap, bounded sizes, and a strict grammar for placeholders such as `$first_flight_date:<step_id>`                                                                                                                                                                                                    |
| **L2** | **Validate every call before it is sent:** the tool exists in the **pinned manifest**, it is within the sub-agent's scope, the arguments validate against the **agent-owned** schema (types, patterns, bounds, no unknown arguments), and resolved placeholders are real values (an ISO date, never `null`)                                                                                                           |
| **L3** | **Bounded repair loop.** On a violation, retry up to a small configured number of times (default two), feeding back a **sanitized, structured list of violations** (field and rule) and nothing else: no raw tool text and no server internals. Each attempt is logged and counted against the run budget (C-12). After the last attempt, **fail closed** with a clear message. A partly valid plan is never executed |
| **L4** | **Execution-time handling.** Classify tool errors with the SP03 taxonomy: `invalid_arguments` goes through the repair path once, `upstream_unavailable` gets bounded backoff, the rest stop. Results are parsed into typed models and rejected if they do not match their schema (C-06), replacing the text-block reassembly used today                                                                               |
| **L5** | **The server validates again, independently** (SP03 TASK-3.9), because it cannot assume its caller is well-behaved                                                                                                                                                                                                                                                                                                    |

**Boundary with TASK-4.6.** This task decides whether a call is _well-formed and contract-valid_. TASK-4.6 decides whether it is _permitted_ (scope, intent, approval). Both run before any call, and a call must pass both.

**Observability.** Structured events `plan_validation_failed`, `plan_repaired` and `tool_call_rejected`, carrying field names and rule IDs but never argument values (the SP00 logging rules), and metrics for first-pass validity rate, repair success rate and attempts per run (SP06 TASK-6.4). A model that keeps failing validation is visible, and the router (SP06 TASK-6.1) can escalate to another free model.

**Tests (deterministic, free).** A "flaky planner" mock provider returns, on demand: text that is not JSON, JSON wrapped in prose, wrong types, missing fields, an unknown tool, an invented argument, a dependency cycle, duplicate step IDs, an oversized plan, a placeholder that resolves to nothing, a plan that becomes valid after one repair, and a plan that is never valid. Tests assert that nothing invalid reaches a server, that repair is bounded, and that the failure is clean (scenario S-16 in the threat model).

## Exit Criteria

- Killing the process mid-run and restarting resumes from the last checkpoint.
- Each sub-agent can see and call only its own MCP tools; an out-of-scope call is refused and logged.
- An out-of-policy booking halts for approval and completes or aborts correctly on the manager's decision.
- A state-changing tool cannot run without approval, regardless of what the model or the server says about it.
- A plan that drifts from the user's request or references a tool outside the sub-agent's graph is rejected.
- A run that exceeds its step, tool-call, token or time budget stops cleanly with a clear outcome; a runaway loop is broken.
- A tool or server can be disabled by configuration without a code deploy.
- The AI component inventory (started in SP03) lists every agent, its model provider and its prompts.
- No tool call is executed unless the plan and that call passed validation against typed models and the pinned tool contracts; an invalid plan gets at most the configured number of repair attempts and then fails closed with a clear message, and no malformed call ever reaches an MCP server (proven by the flaky-planner tests).
- Long-term memory (stage M1) is written only by deterministic code from trusted sources, is isolated per user in the database, expires, and can be completely forgotten; the cross-user leakage, poisoning and forgetting tests pass.
- Every prompt is produced by the single assembler; the layout-contract tests (prefix stability, forbidden content, canonical serialization, append-only history and the cache-simulator regression) pass in CI, and the agent behaves identically with caching disabled.

## Key Risks

Framework lock-in; checkpoint schema evolution; keeping mock mode working for offline tests (it is also what lets the security tests run for free, so it must be able to simulate hostile model behavior); approval fatigue if too many tools are classified state-changing; repair loops burning the free LLM budget (attempts are bounded and counted in the run budget); memory features growing beyond what a portfolio project needs (the staged plan lets work stop after M1).
